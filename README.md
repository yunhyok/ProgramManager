# Program Manager 0.3.0

개인 개발 프로그램을 트레이의 목록에서 실행하고, GitHub Releases의 프로그램을 내부망 PC에 배포하는 Windows 앱입니다. **호스트에서 배포할 저장소를 선택하면 클라이언트는 그 목록에서 설치합니다.** 인터넷이 없는 클라이언트도 사용할 수 있습니다.

설치 파일은 설치 요청이 있을 때 호스트가 다운로드합니다. 설명과 릴리스 이력도 요청할 때 HTML로 만들어 전달합니다. 사용하지 않은 임시 파일은 주기적으로 정리하며, 기존에 등록한 실행 목록은 그대로 유지합니다.

## 어디에서 무엇을 하나요?

| 화면 | 용도 | 처음 할 일 |
| --- | --- | --- |
| **내 프로그램** | 이 PC에 설치된 프로그램 실행·목록 정리 | 기존 항목을 선택해 **실행**, 필요한 EXE/LNK만 추가 등록 |
| **배포 카탈로그** | 호스트가 공유한 프로그램 설명 확인·설치·업데이트 | **설정**에서 연결 코드 등록 후 **목록 새로고침** |
| **호스트 관리** | 배포할 GitHub 저장소 선택·릴리스 목록 동기화 | **호스트 켜기** 선택 |

호스트도 같은 앱에서 자신의 프로그램을 설치할 수 있습니다. 창을 닫으면 트레이에 남으며, 트레이 메뉴의 **종료**로 완전히 종료합니다.

트레이 아이콘을 **오른쪽 클릭**하면 메뉴 맨 위에 최근 실행한 프로그램이 최대 5개 표시됩니다. 항목을 클릭하면 바로 실행합니다. Manager에서 실행한 등록 프로그램만 중복 없이 최근 순서로 기록하며, Manager를 다시 실행해도 유지합니다. 등록 이름·경로를 편집하면 최근 항목에도 반영되고, 등록을 제거하면 최근 목록에서도 사라집니다. 과거 실행 이력은 자동으로 채우지 않으므로 처음에는 비어 있습니다.

## 빠른 시작

**개발 PC / 호스트 — 인터넷과 내부망 연결이 있는 PC**

1. **호스트 관리 → 호스트 켜기**를 누릅니다. **설정**에서 역할과 클라이언트가 접근할 이 PC의 주소·포트를 확인하거나 변경할 수 있습니다.
2. **GitHub 설정**에서 계정을 연결하고 **저장소 선택**을 엽니다. GitHub CLI의 기존 로그인 또는 호스트에 저장하는 토큰을 사용합니다. 저장소별 배포 가능 여부와 사유를 확인해 선택한 뒤 **선택한 저장소 동기화**를 누릅니다. 이후에는 **GitHub 동기화**로 새 버전을 확인합니다.
3. **연결 코드**를 사용할 PC에 전달합니다. Program Manager를 트레이에서 실행해 두면 요청받은 설치 파일과 설명을 내부망으로 전달합니다.

**사용 PC / 클라이언트 — 인터넷 연결 불필요**

1. Program Manager **0.2.0 이상**에서 **설정**에 호스트의 연결 코드를 등록합니다. GitHub 계정이나 토큰은 입력하지 않습니다.
2. **배포 카탈로그 → 목록 새로고침**을 누르고 프로그램을 선택합니다. **오프라인 설명**에서 용도와 변경 내용을 확인합니다.
3. **설치 / 업데이트**를 선택하고 설치를 확인합니다. 다운로드와 크기·SHA-256 검증 후 설치 프로그램이 실행됩니다. 설치를 마치고 실행 경로를 확인하면 **내 프로그램**에서 실행할 수 있습니다.

자세한 사용법과 문제 해결은 앱의 **도움말** 또는 [설치에 포함되는 오프라인 도움말](docs/guide.html)을 참고하세요. 배포 규칙과 운영 예시는 [GitHub 배포 안내](docs/github-distribution.md)에 있습니다.

**도움말**과 **오프라인 설명**은 Program Manager 안에서 열리므로 별도의 브라우저가 필요하지 않습니다.

## 설치

| 컴퓨터 | 설치 파일 | 런타임 |
| --- | --- | --- |
| Windows 10/11 64비트 | `ProgramManager-Setup-0.3.0.exe` | .NET 8 포함 |
| Windows 7 SP1 / 8 계열 | `ProgramManager-Setup-0.3.0-win7.exe` | .NET Framework 4.8 사전 설치 필요 |

기본 설치 위치는 `%LOCALAPPDATA%\Programs\Program Manager`입니다. 시작 메뉴에서 실행할 수 있고, 바탕화면 바로가기는 기본으로 만들지 않습니다. Windows 로그인 시 자동 실행은 설치 옵션 또는 앱 설정에서 선택합니다.

이미 등록한 프로그램의 설치 위치와 실행 경로는 유지됩니다. **목록에서 제거**는 대상 프로그램을 삭제하지 않습니다. `.lnk` 등록 시에는 Manager 데이터 폴더에 바로가기를 복사하므로 실행을 확인한 후 바탕화면 바로가기를 정리할 수 있습니다. 대상 EXE 파일 자체는 원래 위치에 두세요.

## Program Manager 자체 업데이트

0.3.0부터 Manager가 시작할 때와 실행 중 **6시간마다** 새 버전을 확인합니다. 자동 확인은 기본으로 켜져 있으며 **설정**에서 끌 수 있습니다. 새 버전마다 트레이 알림을 한 번 표시합니다. Windows 알림 설정에 따라 알림이 보이지 않아도 트레이 메뉴는 사용할 수 있습니다.

1. 트레이 아이콘을 오른쪽 클릭하고 **관리 프로그램 업데이트 확인**을 선택합니다. 배포 카탈로그의 다른 프로그램 업데이트와 구분되는 기능입니다.
2. 새 버전이 있으면 버전이 표시된 **업데이트 및 재시작** 항목을 선택하고 설치를 확인합니다.
3. 진행 상태를 보며 다운로드를 기다립니다. 크기·SHA-256 검증이 끝나면 Manager를 종료하고 설치한 뒤 기존 데이터로 다시 시작합니다. 새 버전 확인이나 알림 표시만으로 설치하지 않으며, 사용자가 업데이트 실행을 선택하고 확인해야 진행합니다.

호스트에 연결된 클라이언트는 **0.3.0 이상 호스트**를 통해 Manager 업데이트를 받아 인터넷 없이 사용할 수 있습니다. 호스트가 이전 버전이면 호스트부터 업데이트하세요. 호스트 PC와 호스트에 연결되지 않은 PC는 공개 저장소 [yunhyok/ProgramManager](https://github.com/yunhyok/ProgramManager)의 Releases를 직접 조회하며 추가 GitHub 인증 정보가 필요하지 않습니다.

Manager의 새 버전 확인에는 호스트의 인터넷 연결이 필요합니다. 설치 전에 기존 Manager 파일을 임시 백업하고, 설치가 실패하면 이전 파일을 복구한 뒤 다시 실행합니다. 복구까지 실패하면 설치 로그와 수동 복구 안내를 표시합니다. 등록 목록과 설정 데이터는 이 파일 교체 대상에 포함하지 않습니다.

숫자 태그의 정식 Release에서 이 PC의 Windows에 맞는 Manager 설치 파일만 사용합니다. Windows 7용 파일이 없으면 Windows 10/11용 파일을 대신 제안하지 않습니다. 일반 프로그램의 GitHub 배포에 필요한 최소 클라이언트 버전은 계속 0.2.0입니다.

## 배포 동작

- **저장소 선택**은 Release와 설치 파일의 메타데이터를 먼저 검사해 상태·사유를 표시합니다. 설치 파일 자체는 받지 않습니다. 검사·동기화 중에는 화면 하단에 저장소 이름과 처리 수/전체 수가 표시됩니다.
- 배포할 수 없는 새 저장소는 선택할 수 없습니다. 파일 후보가 모호하면 Windows별 파일 이름 패턴을 수정하고 **다시 검사**합니다. 이미 선택했던 저장소가 검사에 실패해도 체크는 유지되며, 체크를 해제해 배포 대상에서 뺄 수 있습니다.
- 동기화는 정상 저장소를 갱신하고 실패 사유를 따로 요약합니다. 실패한 저장소에 이전 게시 항목이 있으면 유지합니다. 동기화를 취소하면 현재 게시 목록을 유지합니다.
- 배포 버전은 `v1.2.3` 같은 숫자 태그의 정식 **Releases**를 기준으로 합니다. 조회한 최근 100개 Release 중 정식 버전을 최대 30개 가져옵니다. 브랜치의 최신 커밋, Draft, Prerelease, 소스 ZIP은 설치 대상으로 사용하지 않습니다. 권한이 있는 비공개 저장소도 사용할 수 있습니다.
- Windows 10/11용과 Windows 7용 EXE/MSI 설치 파일을 별도로 선택합니다. 자동 판별이 모호하면 저장소별 파일 이름 패턴을 지정합니다. Windows 7용이 없으면 다른 OS용 파일로 대체하지 않습니다.
- 목록 동기화는 메타데이터를 가져옵니다. 설치 파일 전체를 미리 받지 않으며, 설치 요청 시 필요한 파일을 받아 검증하고 캐시합니다.
- **설명 / 이력**은 이미 동기화한 메타데이터를 보여줍니다. **오프라인 설명**은 요청 시 README와 릴리스 이력을 자체 포함 HTML로 만듭니다. 제목·본문·코드 블록을 표시하며, 복잡한 서식과 링크는 텍스트로 남습니다. 외부 웹사이트·이미지·첨부파일은 자동 복제하지 않습니다.
- 설명 캐시는 날짜가 바뀌어도 재사용합니다. 동기화한 프로그램·릴리스 정보가 바뀌거나 캐시가 정리되면 다음 요청 때 새로 받습니다. README만 바뀐 경우 **임시 파일 정리** 후 **오프라인 설명**을 다시 엽니다.
- 임시 파일은 기본 7일간 사용하지 않으면 정리 대상이 됩니다. 보관 기간은 **GitHub 설정**에서 1~30일로 정합니다. 앱 시작 시와 실행 중 매시간 정리하며, 수동 정리는 사용 중인 파일을 건너뜁니다. 설치된 프로그램·설정·배포 목록은 정리 대상이 아닙니다.
- 클라이언트는 인증서 지문을 확인하는 TLS 1.2 연결로 호스트에 접근합니다. GitHub 인증 정보는 호스트에서만 사용하며 클라이언트에 전달하지 않습니다.

호스트 사용자가 로그인해 있고 Program Manager가 실행 중이어야 파일을 제공할 수 있습니다. 기본 TCP 포트는 `45672`입니다. 같은 내부망에서 접근 가능하도록 호스트 주소와 Windows 방화벽 설정을 확인하세요. 연결 코드에는 공유 비밀이 포함되므로 사용할 PC에만 전달합니다.

## 데이터와 실행 옵션

기본 데이터 폴더는 `%LOCALAPPDATA%\ProgramManager`입니다.

| 경로 | 내용 | 임시 파일 정리 |
| --- | --- | --- |
| `settings.json`, `shortcuts\` | 설정·로컬 실행 목록·복사된 바로가기 | 유지 |
| `repository\`의 메타데이터 | 호스트 배포 목록·릴리스 정보 | 유지 |
| `identity\` | 보호된 호스트 인증 정보 | 유지 |
| `repository\temp\` | 호스트의 설치 파일·설명 캐시 | 정리 대상 |
| `temp\` | 클라이언트의 임시 다운로드·설명 | 정리 대상 |
| `cache.json` | 마지막으로 확인한 호스트 목록 | 유지 |

직접 입력한 GitHub 토큰과 호스트 연결 정보는 Windows 사용자 계정으로 보호됩니다. 다른 PC나 Windows 계정에는 인증 정보를 다시 설정하세요. 제거 프로그램은 사용자 데이터 폴더를 삭제하지 않습니다. 임시 파일 정리는 Windows의 전체 Temp 폴더를 비우지 않습니다.

```powershell
# 창을 띄우지 않고 트레이에서 시작
ProgramManager.exe --tray

# 별도의 데이터 폴더로 실행 (개발 및 분리된 로컬 확인용)
ProgramManager.exe --data-dir "C:\Temp\ProgramManager-check"
```

## 빌드와 검증

Windows, .NET SDK 8, Inno Setup 6.3 이상 6.x가 필요합니다. .NET Framework 참조 어셈블리는 NuGet으로 복원합니다. Windows 7용 설치 프로그램 호환성을 위해 Inno Setup 6을 사용합니다.

```powershell
./tools/build.ps1

# 컴파일러가 기본 경로에 없을 때
./tools/build.ps1 -InnoCompiler "C:\Tools\Inno Setup 6\ISCC.exe"
```

스크립트는 두 대상 프레임워크의 빌드와 검사를 실행한 뒤 아래 결과물을 만듭니다. 게시 출력 폴더 두 곳은 빌드할 때 새로 생성합니다.

| 출력 | 위치 |
| --- | --- |
| Windows 10/11 실행 파일 및 런타임 | `artifacts/publish/win10-x64/` |
| Windows 7용 실행 파일 및 의존 파일 | `artifacts/publish/win7/` |
| 두 설치 파일 및 `SHA256SUMS.txt` | `artifacts/installers/` |

`.github/workflows/build.yml`은 Windows 빌드·검사 후 두 설치 파일과 `SHA256SUMS.txt`를 버전별 Actions 아티팩트로 보관합니다. 공개 저장소 `yunhyok/ProgramManager`에 프로젝트 버전과 일치하는 `v` 태그를 push하면, 성공한 빌드의 세 파일만 GitHub Release로 게시합니다. 게시 전 원격 태그의 커밋과 설치 파일 해시를 확인합니다. 일반 브랜치 push·Pull Request·수동 실행은 Release를 게시하지 않습니다.

자체 업데이트와 현재 버전의 확인 범위는 [0.3.0 검증 기록](docs/verification-0.3.0.md)을 참고하세요. 이전 결과는 [0.2.2 저장소 검사·동기화](docs/verification-0.2.2.md), [0.2.1 최근 실행 메뉴](docs/verification-0.2.1.md), [0.2.0 GitHub 배포](docs/verification-0.2.0.md), [0.1.1 UI](docs/verification-0.1.1.md), [0.1.0 배포](docs/verification.md)에 있습니다. Windows 7 실기기와 두 번째 물리 PC에서의 설치·통신은 별도 확인이 필요합니다. 최신 Windows에서 `net48`을 실행한 결과만으로 Windows 7 호환성을 확정하지 않습니다.

설치 프로그램의 실제 설치 위치는 제품마다 달라 사용자가 실행 경로를 확인합니다. 배포 프로그램의 원격 무인 설치·자동 롤백, 호스트 자동 검색, Windows 서비스와 인터넷 중계는 제공하지 않습니다.

## IntraDrop 통합

현재 구현은 IntraDrop의 트레이 실행, 사용자별 설정과 인증된 연결 방식을 참고합니다. 카탈로그·다운로드 로직은 `src/ProgramManager.Core`, 화면은 WinForms 앱에 있습니다. 향후 IntraDrop과 통합할 때 공통 코어를 사용할 수 있으며, 현재 두 앱의 데이터와 실행은 독립적입니다.
